# Эксплуатация: диагностика и действия при блокировке

## Регламент обслуживания

| Как часто | Что делать |
|---|---|
| Постоянно | Мониторинг доступности сервера с российского адреса |
| Раз в 1–2 месяца | `bash scripts/05-update-xray.sh` |
| Раз в месяц | `apt update && apt upgrade` на сервере |
| Раз в квартал | Проверить, что резервный сервер и AmneziaWG реально работают |
| При смене устройства | Отозвать старый ключ: `bash scripts/02-add-client.sh --remove <имя>` |

Резервный канал, который никогда не проверяли, — это не резервный канал.
Раз в квартал переключайтесь на него на день.

## Мониторинг

Самый простой вариант — cron на любой машине в России, которая всё равно работает
постоянно (домашний сервер, роутер, мини-ПК):

```cron
*/10 * * * * /path/to/scripts/04-healthcheck.sh 203.0.113.10 www.samsung.com >/dev/null || \
             curl -s "https://api.telegram.org/bot<TOKEN>/sendMessage?chat_id=<ID>&text=VPN%20недоступен"
```

Более удобный вариант — **Uptime Kuma** на дешёвом VPS: она умеет проверять TCP-порт
и слать уведомления в Telegram. Ставьте её **не на тот же сервер**, что и VPN —
иначе она не сможет сообщить о его падении.

## Что делать, когда перестало работать

Диагностика идёт от простого к сложному. Не переустанавливайте сервер, пока
не прошли этот список.

### Шаг 1. Сервер вообще жив?

```bash
ssh root@<IP>              # с обычного интернета
systemctl status xray
journalctl -u xray -n 50
```

Если SSH не проходит — попробуйте зайти через веб-консоль хостера (VNC/KVM в панели).
Живой сервер, недоступный по сети, — это признак блокировки IP, а не поломки.

### Шаг 2. Проверка снаружи

```bash
bash scripts/04-healthcheck.sh <IP>
```

Запускайте **дважды**: с российского интернета и с любого зарубежного (например,
через второй сервер: `ssh root@<IP2> 'bash -s' < scripts/04-healthcheck.sh <IP1>`).

| Результат из РФ | Результат извне | Диагноз |
|---|---|---|
| ok | ok | Проблема на клиенте, не на сервере |
| fail на TCP | ok | **IP заблокирован в России** |
| fail на TCP | fail | Сервер лежит или фаервол хостера |
| ok на TCP, fail на TLS | ok | DPI рвёт соединение по сигнатуре |
| сертификат не совпал | ok | Сайт-маскировка стал недоступен или MITM |

### Шаг 3. Действия по диагнозу

**IP заблокирован в России.** Единственное решение — новый адрес.

```bash
# 1. Переключите клиентов на второй сервер (ссылка уже должна быть у них)
# 2. Закажите смену IP у хостера — обычно тикет и 1–3 €
# 3. После смены обновите состояние и перевыпустите ссылки:
bash scripts/01-install-reality.sh    # переустановит конфиг с новым IP
bash scripts/02-add-client.sh --list  # новые ссылки для всех клиентов
```

Ключи Reality при этом можно оставить прежними — меняется только адрес.
Если хостер IP не меняет, дешевле взять нового провайдера, чем спорить.

**DPI рвёт соединение по сигнатуре** (TCP открыт, TLS не проходит). Обычно значит,
что порт 443 на вашем адресе попал под эвристику. Попробуйте по порядку:

```bash
# 1. Сменить сайт-маскировку — иногда конкретный SNI попадает под фильтр
DEST=www.nvidia.com bash scripts/01-install-reality.sh

# 2. Обновить Xray — свежая версия могла получить обход новой эвристики
bash scripts/05-update-xray.sh

# 3. Перейти на резервный канал, пока разбираетесь
bash scripts/03-install-amneziawg.sh
```

**Сайт-маскировка стал недоступен.** Проверьте кандидата и смените:

```bash
source scripts/lib.sh && check_dest www.samsung.com && echo ok || echo "не годится"
DEST=<новый-сайт> bash scripts/01-install-reality.sh
```

**Проблема на клиенте.** Чаще всего: клиент не обновил geodata (правила маршрутизации
устарели), сбилось системное время (TLS не согласуется при расхождении больше
пары минут), или включён другой VPN/прокси. Проверьте время в первую очередь.

## Отдельный случай: не подключается SSH, хотя сервер жив

Симптом: `ssh: connect to host <IP> port 22: Connection timed out`, при этом
в VNC-консоль хостера вы заходите нормально. Обратите внимание на формулировку:
`timed out`, а не `refused` — пакеты отбрасываются по пути, сервер их не отвергает.

Разделить причины помогает внешняя проверка порта с узлов в разных странах,
например через `check-host.net/check-tcp?host=<IP>:22`:

| Результат | Диагноз | Решение |
|---|---|---|
| Европа подключается, все узлы РФ — таймаут | IP заблокирован в России | Тикет на смену адреса |
| Не подключается ниоткуда | Порт закрыт хостером или sshd не слушает | Список закрытых портов в панели, `systemctl is-active ssh` |
| Подключаются все, включая РФ | Исходящий 22 режет ваша сеть | Перенести SSH на другой порт |

Единичный выпавший узел при десятках успешных — особенность маршрута конкретного
оператора, а не блокировка.

Третий случай встречается чаще, чем кажется: часть российских провайдеров закрывает
исходящий 22-й порт, чтобы с их сетей не сканировали чужие серверы. Проверяется
попыткой достучаться на 22-й порт любого заведомо живого хоста
(`Test-NetConnection github.com -Port 22` в PowerShell). Лечение — перенос sshd
на другой порт, через VNC-консоль:

```bash
echo 'Port 2222' > /etc/ssh/sshd_config.d/99-port.conf
systemctl restart ssh
ss -tlnp | grep 2222
```

После этого подключайтесь как `ssh -p 2222 root@<IP>`, а `00-hardening.sh`
запускайте с указанием порта, иначе фаервол откроет 22-й и отрежет вам доступ:

```bash
SSH_PORT=2222 bash scripts/00-hardening.sh
rm -f /etc/ssh/sshd_config.d/99-port.conf   # скрипт пишет свой конфиг
```

На работу VPN это не влияет: Reality слушает 443-й порт, а его не режет никто —
для сети это обычный HTTPS.

## Признаки того, что пора менять адрес заранее

Не ждите полной блокировки, реагируйте на деградацию:

- скорость упала в разы без изменений на стороне сервера;
- соединение рвётся каждые несколько минут и переустанавливается;
- работает на проводном интернете, но не работает у мобильного оператора;
- работает у одного провайдера в городе и не работает у другого.

Это типичная картина «адрес под подозрением, но ещё не в блоке». Профилактическая
смена IP занимает полчаса, экстренная — вечер.

## Гигиена, продлевающая жизнь сервера

1. **Не более 10 ключей на сервер.** Больше — характерный профиль коммерческого
   сервиса, а не личного туннеля.
2. **Не публикуйте ссылки.** Ни в чатах, ни на форумах, ни «другу друга». Утёкшая
   ссылка живёт до первого сканирования.
3. **Не гоняйте торренты через сервер.** Абузы — самая частая причина расторжения
   договора хостером. В конфигах комплекта это уже заблокировано.
4. **Не ставьте на сервер ничего лишнего.** Панели, веб-морды, Docker с открытыми
   портами — всё это добавляет сигнатур и уязвимостей. Порт 443 и SSH, больше ничего.
5. **Разнесите SSH и VPN по времени настройки.** Не оставляйте SSH на 22 порту
   с парольным входом — `00-hardening.sh` это закрывает.
6. **Не подключайтесь к своему серверу из сетей, где вы его настраивали публично** —
   например, из корпоративной сети с полным логированием.

## Если нужен «переезд без переустановки клиентов»

Когда серверов становится три и больше, а пользователей — десяток, менять ссылки
вручную при каждой смене IP становится мучением. В этот момент имеет смысл
поднять **подписку**: клиенты один раз получают URL, а вы за ним меняете список
серверов.

Минимальный вариант без панели: статический файл со списком ссылок в base64,
отдаваемый nginx с отдельного дешёвого хоста по HTTPS. Все перечисленные клиенты
умеют такие подписки и обновляют их автоматически.

Полноценный вариант: **Remnawave** или **Marzban** — панели с подписками,
лимитами трафика, сроками действия и мультисерверными нодами. Оправданы примерно
от трёх серверов; до этого сложность превышает пользу.
